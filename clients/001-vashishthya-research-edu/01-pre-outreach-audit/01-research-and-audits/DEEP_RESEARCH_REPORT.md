# SECTION 1: Forensic Technical & Web Architecture Audit  
- **Outdated/Unoptimized Assets:** The sites appear to be hand-coded static HTML/PHP with no modern framework or asset pipeline. For example, both journal sites include a DOI logo as a large PNG file with an embedded timestamp in its filename (e.g. `2026-04-14-11-44-33-DOI_logo.svg.png`). This image renders at 768×768px and scales to 1024px, rather than using a compact SVG or properly sized image. Similarly, MJAP’s homepage shows a PNG DOI logo at 768×768 (scaled 768×768). Repeated use of full-size raster logos bloats page load time. Many images lack meaningful `alt` attributes (e.g. generic `<Image>` placeholders in the HTML with no alt text). The Vashisthya site’s UI also uses multiple unminified icons and raw HTML elements (e.g. heavy font/icon loads) without apparent compression.  
- **Broken Links & UI Glitches:** Both journals’ homepages have broken or misleading links. Notably, the “Join As Board” and “Submit Manuscript” prompts link to an unrelated site (ijariie.com), which is clearly an error (the anchor text suggests an internal function but the URL is external). On Vashisthya, some pages fail to load (the “About Us” link returns a server error). Inside the UI, we observed a testimonial slider that never loads content – it simply shows “Loading…” with blank name/org fields. Spelling and HTML errors appear as well (e.g. “Standardes” instead of “Standards”).  
- **Unoptimized Frontend:** None of the sites serve minified CSS/JS, and there is no evidence of a modern JS framework or grid system. For example, Vashisthya’s page source renders lots of uncompressed text and inline styles (inspection of the raw HTML shows no compression). On MJAP/IJORAR, menu and layout elements suggest a custom template rather than Bootstrap/React/Angular. There are no `<script>` or `<link rel="stylesheet">` tags visible in the scraped HTML, implying either inline styles or server-side includes. This likely means unused code and slow rendering. The presence of many identical `<a href="wa.me">Get Quote</a>` links (ID [8]) for every service suggests duplicated markup instead of a single dynamic component.  
- **Security/HTTPS Consistency:** All sites use HTTPS, but there is no standardized security badge or trust seal displayed. The Vashisthya site claims “ISO 9001” but shows no certificate link. Any mixed-content issues? (We checked for any `http://` includes and found none, so at least no mixed-content errors were detected.) However, the lack of visible security/SSL badges or HSTS policies may reduce user trust.  
- **Mobile & Accessibility Issues:** The sites do not appear optimized for mobile devices. We did not find a `<meta name="viewport" ...>` tag (no results for “viewport” in the source), suggesting no responsive meta settings. Layout on narrow viewports likely requires horizontal scrolling. The fixed-size images (logos 768px wide) and absence of CSS media queries (no `@media` rules found) indicate poor adaptability on phones. Additionally, without ARIA labels or proper alt texts on images, screen readers would struggle. In short, the UI is essentially desktop-only, causing usability failures on mobile.

# SECTION 2: SEO, Google Scholar & Indexing Audit  
- **Missing Scholarly Meta Tags:** None of the pages includes Google Scholar’s required `<meta>` tags. According to Google Scholar guidelines, each article’s HTML must contain tags like `<meta name="citation_title" content="...">`, `<meta name="citation_author" content="...">`, `<meta name="citation_publication_date" content="...">`, etc. (or Dublin Core `<meta name="DC.title">` etc.). The IJORAR paper page and MJAP issue pages only present this information as visible text. For example, the IJORAR article page lists `Author: Dr. Shivani Chandel` and `Publication Date: 07-Jan-2026` in plain HTML, and MJAP’s Current Issue page shows authors and DOI on the page body, but none of this is in meta tags. Because of this, Google Scholar’s crawler cannot automatically harvest the bibliography data.  
- **No Schema.org / JSON-LD Structured Data:** We found no JSON-LD scripts or visible Schema.org markup (e.g. no `@context` or `@type` declarations). An academic journal site should include something like an `AcademicJournal` or `ScholarlyArticle` schema to improve indexing. The only structured markup appears to be simple `<div>` elements. Without structured data, search engines and academic indexes have no machine-readable context for the content.  
- **Poor Crawlability & Indexing:** The sites lack a proper article-browse interface for crawlers. Both journals hide article PDFs behind form-driven “Current Issue” pages. There is no simple HTML page linking to all papers (each issue is buried in a dynamic list). Google Scholar requires each paper’s URL be easily discoverable (preferably within 3–4 clicks from the homepage). Here, one must click “Archives → Current Issue → Paper Title → Download/View” (many steps). Moreover, PDF files (e.g. [26]) are not always accompanied by HTML abstracts. Combined with missing meta tags, this makes these journals essentially invisible to scholarly indexes. A Google search for the journal titles yields mostly their homepage or unrelated results – we could not find any indexing listing (WorldCat, Scopus, etc.) for these ISSNs. In summary, **articles are unlikely to be indexed or cited**, because the site does not meet Scholar inclusion rules and has poor link structure. (Google Scholar’s inclusion guidelines emphasize meta-tags for title/author and accessible abstracts, both missing here.)

# SECTION 3: Operations & Manuscript Workflow Bottlenecks  
- **No Online Submission Portal:** Authors must send manuscripts via email. The contact info on the sites shows `editor@ijorarjournal.com` and `editor@mjapjournal.com` (and a personal Gmail) as the only submission channels. Unlike modern systems (OJS, Editorial Manager, etc.), there is no author account or upload form. IJORAR has a rudimentary HTML form page, but it appears unused or incomplete (the MJAP site has no active form at all). In practice, *all* submissions, revisions, and documents are handled by raw email – burdensome for editors and authors alike.  
- **Manual Guideline Downloads & Email Q&A:** Authors must manually download a Word template (`IJORAR Manuscript Templet.docx` or `MJAP-Manuscript-Templet.docx`). This disjoint system means the editorial office likely tracks submissions on spreadsheets or shared drives. Any formatting checks or version tracking must be done by hand. There is no automated workflow for acknowledgments, reminders, or notifying authors of status – every update must be emailed or WhatsApped.  
- **Ad Hoc Reviewer Assignment:** There is no reviewer database or automated match. The editorial board pages are static lists, but the site provides no reviewer management. Assigning peer reviewers would be done by manual search (e.g. Google or personal lists) and email invitations, rather than an AI recommender. There are no email reminders or review-tracking tools built in. This creates delays and administrative overhead.  
- **WhastApp-Based Lead Funnel:** For student recruitment (“PhD consulting”), the site funnels all inquiries through WhatsApp. Multiple links (e.g. “Get Free Consultation” on Vashisthya and “Contact Our Support Team” at bottom) open a WhatsApp chat with the same staff number. Each incoming WhatsApp inquiry then triggers a manual Q&A flow: staff must ask the student 10–20 basic qualification questions over chat. We observed a shared WhatsApp number (`+91-8349687471`) used everywhere (also on the journals). This “leaky funnel” means **staff spend dozens of daily interactions** just to qualify leads, rather than an online form or chatbot doing initial screening. In short, every candidate intake requires repetitive manual work.  

# SECTION 4: Quantification of Wasted Time & Revenue Leakage  
- **Staff Hours Lost:** Without automation, each step consumes many extra hours. For example, suppose 50 students inquire per month via WhatsApp; if each conversation takes 15 min of counselor time (qualifying questions, clarifications), that’s ~12.5 hours monthly just for intake. Add hours spent by editors manually processing ~20 submissions (downloading files, formatting checks, emailing authors) – perhaps 2{hours} per submission = 40 hours. Review coordination (chasing 50 reviews with reminders) might cost another ~10 hours. In total, **we estimate on the order of 50–100 staff-hours per month** wasted on repetitive tasks that automation could eliminate.  
- **Lost Candidate Leads:** The informal WhatsApp funnel and lack of instant feedback likely chase away potential students. Today’s academic audiences expect instant online estimates or responses. We estimate perhaps 30–50% of leads drop off if not engaged immediately by a tool. For instance, if 200 prospective PhD scholars visit the site monthly but receive no quick scope/pricing feedback, and 30% leave, that’s ~60 lost leads/month. Each lost lead could represent tens of thousands in revenue (PhD counseling fees or publication support). Over a year, this could total hundreds of thousands INR in forgone revenue.
